관리자 화면을 만들고 미들웨어로 /admin 을 막으면 "관리자 기능은 잠갔다" 는 느낌이 들어요. 그런데 화면이 부르는 API 는 다른 길이에요. 리뷰해 보면 화면은 막혀 있는데 그 뒤의 API 는 열려 있는 경우가 꽤 있어요.

1. matcher 가 API 를 안 덮는다

export const config = { matcher: ['/admin/:path*'] }

이 설정은 /admin 화면만 지나가요. 관리자 화면이 부르는 /api/admin/orders 는 이 미들웨어를 거치지 않아요. 브라우저 개발자 도구에서 API 주소를 보고 직접 부르면 로그인 없이 응답이 와요.

2. 서버 액션은 주소가 없다

Next.js 서버 액션은 페이지 주소가 아니라 액션 단위로 불려요. 페이지를 미들웨어로 막아도 액션 자체를 직접 호출할 수 있어서, 액션 함수 안에서 세션과 역할을 다시 확인해야 해요.

3. 확인 전에 service_role 을 꺼낸다

Supabase 의 service_role 키는 RLS 를 건너뛰어요. 관리자 API 에서 이 키로 DB 를 부르는 건 정상이지만, "이 사람이 관리자인가" 를 확인한 다음이어야 해요. 순서가 바뀌면 RLS 를 켜 둔 의미가 없어져요.

권장 구조

  • 미들웨어는 1차 필터 — matcher 에 /api/admin/:path* 도 넣기
  • API 라우트·서버 액션마다 requireAdmin() 같은 함수 한 줄로 다시 확인
  • 관리자 여부는 클라이언트가 보낸 값이 아니라 서버의 세션·DB 로 판단

확인하는 법

로그아웃한 시크릿 창에서, 그리고 일반 사용자로 로그인한 창에서 관리자 API 주소를 직접 열어 보세요. 401·403 이 나와야 정상이에요.

관리자 권한 체크리스트

  • 미들웨어 matcher 에 API 경로도 들어 있다
  • API 라우트마다 서버에서 역할을 다시 확인한다
  • 서버 액션도 함수 안에서 권한을 확인한다
  • service_role 키는 권한 확인 뒤에만 쓴다
  • 로그인 안 한 상태로 API 를 직접 불러 봤다
  • 일반 사용자 계정으로도 불러 봤다

마치며

화면을 막는 건 "문에 커튼을 치는 것", API 를 막는 건 "문을 잠그는 것" 이에요. 커튼만 쳐 두고 잠갔다고 착각하기 쉬운 자리라, 출시 전에 API 주소를 직접 한 번씩 두드려 보세요.
