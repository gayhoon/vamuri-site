전액 취소는 쉬워요. paymentKey 하나 넘기면 끝이니까요. 그런데 "세 개 중 하나만 환불해 주세요"가 들어오는 순간 코드가 갑자기 어려워집니다. 토스페이먼츠 기준으로, 부분 취소를 붙일 때 리뷰에서 자주 보이는 빈틈을 모았어요.

1. 취소 금액을 화면에서 받는다

취소 API 는 POST /v1/payments/{paymentKey}/cancel 이고, cancelAmount 를 넣으면 부분 취소, 안 넣으면 전액 취소예요. 화면이 보낸 금액을 그대로 넘기면 두 가지가 터져요.

  • 값이 비어서 오면 의도와 달리 전액이 나가요.
  • 남은 금액보다 크거나, 할인·쿠폰을 뺀 실제 결제액과 안 맞는 금액이 그대로 나가요.

서버가 주문 품목·실결제액·지금까지 취소한 합계로 환불액을 다시 계산하세요. 쿠폰이 걸린 주문이면 할인을 품목에 어떻게 나눌지도 미리 정해 두는 게 좋아요. 안 정하면 마지막 품목 환불 때 몇 원이 꼭 남거나 모자라요.

2. 버튼 두 번 = 환불 두 번

관리자 화면에서 환불 버튼을 두 번 누르거나, 느려서 새로고침하면 같은 부분 취소가 두 번 들어가요. 부분 취소는 여러 번 할 수 있는 기능이라 PG 가 "이미 취소됨"으로 막아 주지 않아요.

  • 취소 요청마다 멱등키 헤더(Idempotency-Key)를 붙이세요. 같은 키로 다시 보내면 중복 취소 없이 처리돼요.
  • 키는 요청할 때 만들지 말고, 환불 요청 행을 DB 에 먼저 만들고 그 행의 ID 로 쓰세요. 그래야 재시도해도 같은 키가 나가요.

3. 응답이 끊기면 — 취소됐는지 모른다

타임아웃은 "실패"가 아니라 "모름"이에요. PG 쪽에선 이미 취소됐을 수 있어요. 이때 새 키로 다시 보내면 이중 환불, 그냥 실패 처리하면 장부가 틀려요. 같은 멱등키로 재시도하거나, 결제 조회 API 로 cancels 배열을 보고 판단하세요.

4. 웹훅과 조회를 한 번만 반영하기

부분 취소가 끝나면 결제 상태가 PARTIAL_CANCELED 가 되고, 취소 내역이 cancels 배열에 한 건씩 쌓여요. 웹훅은 재전송될 수 있고, 내 API 응답 처리와 웹훅이 거의 동시에 올 수도 있어요. 각 취소의 transactionKey 를 유니크로 저장해서, 같은 취소를 두 번 반영하지 않게 하세요.

5. 결제수단마다 다른 것

  • 가상계좌 — 입금 전에는 부분 취소가 안 돼요(입금 금액을 바꿀 수 없어서). 입금 뒤 취소하려면 refundReceiveAccount 로 환불받을 계좌를 넘겨야 하고, 승인 응답의 환불 계좌 정보는 결제창을 띄운 뒤 30분 동안만 조회돼요. 받아 두거나 사용자에게 입력받는 화면이 필요해요.
  • 카드 — 부분 취소는 카드사 처리에 3~4영업일이 걸려요. "환불했는데 왜 안 들어와요?" 문의를 줄이려면 화면에 미리 적어 두세요.
  • 휴대폰 결제 — 결제한 달에만 취소돼요. 달이 넘어가면 다른 환불 방법을 준비해야 해요.

부분 환불 체크리스트

  • 취소 금액은 서버가 남은 금액으로 다시 계산한다
  • 취소 요청마다 멱등키를 붙이고 DB 에 먼저 적는다
  • 응답이 끊기면 결제 조회로 cancels 를 확인한다
  • 웹훅·조회 결과는 transactionKey 로 한 번만 반영한다
  • 가상계좌는 입금 전 부분 취소 불가, 환불 계좌를 받아 둔다
  • 카드 부분 취소 3~4영업일을 화면에 안내한다

마치며

결제 승인은 출시 전에 다들 열 번씩 눌러 보는데, 환불은 첫 환불 요청이 와서야 처음 눌러 보는 경우가 많아요. 테스트 키로 "두 번 누르기"랑 "응답 끊기"만 한 번씩 해 보셔도 큰 사고는 거의 막혀요 ㅎㅎ
